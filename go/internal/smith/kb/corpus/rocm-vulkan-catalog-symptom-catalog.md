## Symptom → Cause → Fix Catalog

| Symptom | Backend | Root cause | Fix | Detail |
|---|---|---|---|---|
| Load fails immediately: `radv: Not enough memory for command submission` | Vulkan | Vulkan has a hard ~63 GB ceiling on this host — no unified-memory equivalent exists on the Vulkan path | Switch that mode's `backend` to `rocm` and confirm `GGML_CUDA_ENABLE_UNIFIED_MEMORY=ON` is present in the target slot's sysconfig env file | `pitfalls:backend-selection`, `pitfalls:gtt-ceiling` |
| GPU hang / core dump on the very first `--flash-attn on` request, only on the Poolside (laguna) fork | ROCm | The fork's hand-rolled WMMA flash-attn kernel has no gfx1151 device code — `AMD_WMMA_AVAILABLE` is gated on an RDNA3-only guard that gfx1151 (RDNA3.5) doesn't satisfy, so the call hits `NO_DEVICE_CODE` | Build the Poolside fork **with** `-DGGML_HIP_ROCWMMA_FATTN=ON` — the opposite of every other build on this host, which must have it `OFF` | `pitfalls:gtt-ceiling` (rocWMMA bullets) |
| `n_ctx` reported by `/props` is smaller than configured, with no error anywhere | ROCm or Vulkan | The kernel failed to find one large contiguous GTT block for the KV cache and llama.cpp silently downscales instead of failing | Always verify `n_ctx` via `/props` after every load, never trust the configured value; kernel mitigations `amdgpu.mcbp=0`, `amdgpu.vm_fragment_size=9` | `pitfalls:silent-context-reduction` |
| `rocm-smi --showmeminfo gtt` / `gtt_used_bytes` stay near baseline while a model is clearly loaded and consuming tens of GB | ROCm + unified memory | `GGML_CUDA_ENABLE_UNIFIED_MEMORY=ON` backs allocations with HMM-mapped host RAM, which classic GTT counters cannot see at all | Read `gtt_used_bytes + inference_rss_bytes` additively (already how the collector computes `InferenceRSSBytes`) — never trust `gtt_used_bytes` alone as the footprint for a unified-memory ROCm slot | `pitfalls:gtt-ceiling` |
| A model that used to load at full context/RSS now loads smaller, or a slot reports the wrong model alias | Either | A hand-set per-slot sysconfig line (the unified-memory flag, or a `FOUNDRY_*`/`FORGE_*` divergence) was silently dropped or frozen stale by a rename/re-provision that only wrote fresh files for some slots | Diff the affected slot's live sysconfig env file against a known-good sibling slot; smith's `slot_model_identity` and `binary_paths` checks exist specifically to ground-truth this class of drift every sweep | `pitfalls:gtt-ceiling`, `pitfalls:foundry-forge-env-divergence` |
| GPU utilization reads 60–80% during generation on a large model and looks like wasted capacity | Either | Token generation on large models is memory-bandwidth-limited, not compute-limited — this is the expected, normal range, not evidence of a problem | No action; use throughput (tok/s from `/metrics`) as the real efficiency signal, not GPU% | `pitfalls:backend-selection`, `modelselection:amd-rocm-strix-halo` |
| A large ROCm model's unload SIGABRTs or the unit restart-loops | ROCm | Models above ~80 GB take several minutes to unload; systemd's default `TimeoutStopSec=60` aborts the process mid-unload | Set `TimeoutStopSec=300` on that slot's unit | `modelselection:amd-rocm-strix-halo` |
| A freshly built binary resolves its ROCm libraries fine when run by hand but crashes or silently loads the wrong SDK's libraries under systemd | Build (either backend) | CMake's automatic RPATH only covers a target's *direct* link dependencies — a transitively-linked vendor library (e.g. TheRock's ROCm libs) can fall through to the system `ldconfig` cache, which under an empty systemd environment can resolve to an unrelated ROCm SDK (e.g. ComfyUI's bundled one) instead | Verify resolution with `env -i ldd <binary>` (not a shell with `LD_LIBRARY_PATH` set) before declaring a build done; fix the RPATH at CMake/link time (`CMAKE_BUILD_WITH_INSTALL_RPATH=ON` plus an explicit `$ORIGIN`), never patch it post-hoc with `patchelf` | `diagnosis-trial:rocm-rpath-bug`, `diagnosis-trial:rocm-reusable-lessons` |
| A long-prefill request appears to hang — no response, no crash, no error | ROCm | Known upstream AQL queue-hang behavior on gfx1151 under long prefills, mitigated by `GPU_MAX_HW_QUEUES=4`; can also be genuine GPU queue eviction on very deep prefills | Confirm `GPU_MAX_HW_QUEUES=4` (and the rest of the flag audit) are still set; treat sustained near-zero tok/s from `/metrics` as the hang signal, not GPU%/temperature | `diagnosis-trial:rocm-flag-audit`, `pitfalls:inference-hang` |
| A MoE or large model measurably underperforms its Vulkan equivalent at the same quant on ROCm | ROCm | MXFP4 compute kernels aren't fully optimized on ROCm/gfx1151 (~10 tok/s penalty observed); Vulkan RADV generally wins token-generation throughput on this host regardless of quant | Prefer Vulkan for a mode unless it exceeds the ~63 GB ceiling or specifically needs unified memory | `pitfalls:backend-selection`, `modelselection:amd-rocm-strix-halo` |
