title: A rename that redeploys code but not deployed scripts leaves the running process silently stale

- **`FOUNDRY_*`/`FORGE_*` sysconfig divergence — found 2026-08-25 (security hardening sprint 4 follow-up), same root code path as the bullet above, opposite failure mode.** The 2026-08-24 Foundry→Forge rename renamed `/usr/local/lib/foundry` → `/usr/local/lib/forge` with a plain `mv` (`scripts/migrate-foundry-to-forge.sh` step 2) — path only, content untouched — and separately installed the new `systemd/forge-*.service` units, but never actually deployed the repo's own already-corrected `scripts/start-a{1,2,3,4}.sh` (which read `FORGE_*`) onto the host; the deployed launcher scripts kept reading `FOUNDRY_*` exclusively. Meanwhile `writeServiceFiles` (`go/internal/engine/sysconfig.go`) had, since the rename, only ever written fresh `FORGE_*` lines and blanket-preserved every other line in the file forever — so any `FOUNDRY_*` line frozen at whatever value pre-rename code last wrote it stuck around alongside the fresh `FORGE_*` lines, unrelated to them, forever. Result: the **actually-running llama-server process** on a slot was governed by the frozen `FOUNDRY_*` values while the dashboard/API (reading `FORGE_*`) confidently reported something else. **Confirmed live on ForgeHost**: `a1`/`a2` happened to still agree (their last real pre-rename change coincided with what's loaded now — luck, not correctness); `a3`'s frozen `FOUNDRY_MODEL_PATH`/`ALIAS` pointed at a completely different model (`gemma4-e4b-qat`, smith's old brain) than its fresh `FORGE_*` values (`gemma4-26b-a4b-nothink`); `a4`'s frozen `FOUNDRY_MODEL_ALIAS` named the base sibling (`gemma4-26b-a4b`) while `FORGE_MODEL_ALIAS` said the `-nothink` variant — a same-weights-sibling case, so the actual GGUF loaded would have been right but the process's own self-reported `--alias` (and therefore what a0 routes by) would have been wrong. Neither slot was loaded at discovery time, so nothing was actively wrong that moment — the next load onto either slot, if it changed the model from the frozen legacy state, would have launched the wrong thing while the app reported the right one. **Fixed**: `writeServiceFiles`'s preserve-filter now drops `FOUNDRY_*`-prefixed lines too (not just skips writing them — actively removes them from what it preserves), the corrected launcher scripts were redeployed to `/usr/local/lib/forge/`, and the two live-stale slots' env files were cleaned. **New standing defense**: smith's `slot_model_identity` check (`go/internal/smith/checks_paths.go`) compares the actually-running process's `/props`-reported `model_alias` against the engine's configured belief for every loaded slot every sweep — this is the one check that would have caught this exact class of drift (an env-file-preservation bug is only one possible cause; the check is cause-agnostic ground-truthing, not a special-cased detector for this one incident). A second, narrower gap found in the same investigation: `infra.paths.rocm_bin` pointed at `/opt/forge/llama.cpp/build/bin/llama-server`, whose containing directory doesn't exist — low blast radius in practice (the catalog `builds` table's per-config `binary_path`, written to `FORGE_LLAMA_BIN`, is what real loads actually use; this field is only a last-resort fallback plus a `profile.go` fingerprint-cache-key input), but still wrong; fixed to `build-rocm715`, and smith's new `binary_paths` check (same file) now stats every `infra.paths.{vulkan_bin,rocm_bin}` and every non-empty catalog `builds.binary_path` every sweep so a stale path like this can't go unnoticed again.
